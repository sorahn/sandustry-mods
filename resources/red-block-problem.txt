Dev notes: Door red-square / “opens visually but lava won’t flow”
Game: Sandustry ~0.5.3
Structure: signalGate (player “Door”), 4×4 footprint
Sprite: mods/signalGate.png — 3 frames (closed / open / trapped)

Root cause
A door’s visual state and physical state are tracked separately and can diverge.

Layer	What it controls
spriteIndex / spritesheet
What the player sees
trapped
“Broken” / red-square mode (frame 2)
data.ownsBlocks
Whether this door currently owns the 4×4 Block terrain cells
data.desiredOpen
Intended open/closed after signal / UI
Terrain cells (Block in the 4×4)
Whether sand/lava can actually pass
How it breaks
Close while the 4×4 is not empty (sand, lava, grabber debris, etc.)
Door sets trapped = true and switches to frame 2 (red square / broken look) instead of fully closing.

Open while trapped
Sprite goes to open (frame 1) and trapped is cleared, but Block cells are only removed if ownsBlocks is true.
If ownsBlocks is wrong/false, the door looks open and the physical barrier stays → lava does not flow.
Matches player reports: “opens the texture of the door but not the physical door.”

Save/load / paste resync
Handlers recompute desiredOpen / ownsBlocks and can leave trapped, sprite, and terrain out of sync. Reload often makes it worse (open sprite + red square again).

Deconstruct
Owned Block cells may remain as orphans with no signalGate, so the “wall” persists after the door is gone.

This is not a missing texture. Frame 2 is an intentional trapped/broken presentation; the bug is that open/close does not always keep ownsBlocks + terrain cells consistent with the desired open state, and trapped open does not force a physical clear.

Suggested fix (small, in-engine)
Keep one invariant after every door transition (signal, press, load, paste, deconstruct):

If the door should be open → no door Block cells in its 4×4, ownsBlocks = false, not trapped, open sprite.
If the door should be closed → either fully closed (ownsBlocks = true + Blocks placed) or explicitly blocked-by-contents with a clear UX — but never “open sprite + Blocks still there”.

Concrete changes:

On open (including from trapped)
Always clear the door’s owned Block cells in the 4×4 (or treat them as owned and remove them), then set ownsBlocks = false, clear trapped, set open sprite. Do not gate the terrain clear only on a stale ownsBlocks flag.

On close when the area is occupied
Either refuse close and keep a consistent closed/trapped presentation, or enter trapped without leaving an open sprite + leftover Blocks after a later open. Prefer: trapped means “wanted closed, blocked by contents”; first successful open should still clear Blocks.

On save load / paste
After recomputing signal/desiredOpen, run the same reconcile: sync sprite ↔ ownsBlocks ↔ terrain. Don’t restore trapped + open sprite together.

On remove/deconstruct
If ownsBlocks (or Blocks were created by this door), remove those 4×4 Block cells with the structure.

Optional hardening: when entering trapped, snapshot that the door still “owns” the barrier so the next open always removes it.

Quick repro checklist
Place a door, open it, dump sand/lava into the 4×4, try to close → red square (trapped).
Open again → sprite open, cells still blocked.
Save/load → often still broken / red square.
Deconstruct while desynced → Blocks may remain.
Workaround for players (until patched)
A FluxLoader mod can force reconcile (ownsBlocks + setOpen / clear Blocks). That is only a band-aid; the durable fix is the invariant above in the door open/close and load paths.
